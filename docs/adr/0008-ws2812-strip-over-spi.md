# ADR-0008: Status LEDs on the Pi satellite — a WS2812B strip driven over SPI from Rust

| | |
|---|---|
| **Status** | Accepted and implemented. **Hardware-verified 2026-09-03** on the Pi 5 with the demo (`ws2812-poc`): after the config.txt + reboot SPI enable, the wiring check and the scanner run as designed at the default clock and brightness. The test strip's last LED has a dead green die (a strip defect: that LED's data is regenerated by its neighbour, so the driver cannot cause a one-channel, one-position fault). **In the client since 2026-09-03**: `crates/client/src/led/strip.rs` renders the full vocabulary below (a pattern per phase, an overlay for a gated mic, a fault pattern when the server is away); `LED_STRIP=off` disables it. |
| **Date** | 2026-09-03 |

Not the guide's GPIO 18 PWM path (`rpi_ws281x`), not the Pi 5's PIO, not the `ws2812-spi`/`embedded-hal` stack. The data wire moves from pin 12 to pin 19. |
| **Related** | PRD SENS-2 (client outputs: LEDs) and RTC-2 (`state` messages, the signal the strip renders); `docs/specs/jabra-led.md` (the speakerphone LED ring this strip complements, and the phase tracker both share — `Phase::Offline` was added for the strip); `crates/client/src/led/strip.rs` (the client's sink and animator); `deploy/rpi/` (unit + installer); `Cross.toml` (the cross-build any driver has to survive); `crates/ws2812/README.md` (wiring and usage). |

## Context

The satellite is a Raspberry Pi 5 on 64-bit Pi OS, running the native client as a
system unit (`deploy/rpi/voice-chatbot-client.service`: unprivileged `User=`,
`SupplementaryGroups=audio`), cross-built from the dev machine with `cross` in
Docker against a pinned glibc-2.36 sysroot. Today the only activity indication is
the Jabra Speak2's LED ring (`docs/specs/jabra-led.md`), which exists only while a
Jabra is the speaker. An 8-LED WS2812B strip (5 V, "NeoPixel") was attached to
the Pi following the Core Electronics guide: 5 V and GND from the header, data on
GPIO 18 (pin 12). PRD SENS-2 names LEDs as a client output; RTC-2's `state`
(listening / thinking / speaking / idle) is what the strip will eventually show.

The PoC's job: light the strip from a standalone Rust binary with a recognisable
animation in several colours (a Larson scanner), deployed and run from the dev
machine with one make target, so the driver can be lifted into `crates/client`
unchanged.

### Constraints

1. **It is a Pi 5.** The guide was written on a Pi 4 (p. 3) and its own
   troubleshooting note says NeoPixels do not currently work on the Pi 5
   (p. 14). On the Pi 5 the GPIO, PWM, PCM and SPI blocks live in the RP1 I/O
   chip behind PCIe; the userspace `/dev/mem` + DMA tricks written against the
   BCM2711 register map are gone.
2. **Unprivileged.** The client runs as a plain user; whatever drives the strip
   has to work from a supplementary group, the way `/dev/snd` does via `audio`.
3. **The cross-build.** No native library unless it ships in the `cross` image
   (`Cross.toml`), and `make check` runs clippy `--workspace` on the Mac, so any
   hardware crate must be target-gated.
4. **WS2812 timing.** 800 kHz, 1.25 µs per bit; a 0 is a 0.40 ± 0.15 µs high
   pulse, a 1 is 0.80 ± 0.15 µs; a low of ≥ 50 µs (older parts) or ≥ 280 µs
   (WS2812B-V5) latches the frame. Nothing in Linux userspace toggles a GPIO
   with sub-microsecond accuracy; the waveform has to come from a peripheral.
5. **3.3 V data into a 5 V strip.** WS2812B V_IH is 0.7·V_DD = 3.5 V nominal;
   modern strips accept 3.3 V (guide p. 3), older ones may not.
6. **Power.** 60 mA per LED at full white, 480 mA for eight, within the Pi's
   5 V pin on the official 5 A supply; brightness is capped in software anyway
   (default 0.2, the guide's own habit).

## Candidates

Ways to produce a WS2812 waveform from a Pi, as of September 2026:

| Route | Pin(s) | Pi 5 | Pi 4 | Root | Native code | Notes |
|---|---|---|---|---|---|---|
| PWM + DMA (`rpi_ws281x`) | GPIO 12/13/18/19 | no | yes | yes (`/dev/mem`) | C lib; `rs_ws281x` 0.5.1 (2023, bindgen) wraps an old version | The guide's path. Also takes the PWM audio block (guide: `dtparam=audio=off`). |
| PCM/I2S + DMA (`rpi_ws281x`) | GPIO 21 | no | yes | yes | C lib | Same mechanism on the I2S block. |
| RP1 PIO (`/dev/pio0`, piolib; newer `rpi_ws281x` builds) | any | yes | **no** | yes, or a udev rule | C lib; no Rust crate (crates.io "rp1 pio": nothing) | Keeps GPIO 18. Pi 5-only; a Pi 4 satellite would need a second driver. |
| **SPI0 MOSI (`spidev`)** | GPIO 10 | **yes** | **yes** | **no** (`spi` group) | **none** | The guide's own alternative (`LED_PIN = 10`, p. 10). Hardware-timed bits; SCLK/MISO/CE unused; the strip must be alone on SPI0. |
| Kernel PWM (sysfs) | GPIO 18 | yes | yes | no | none | Static period/duty only; cannot stream a pattern. |
| GPIO bit-bang (gpiod) | any | yes | yes | no | none | Cannot hold 0.4 µs pulses from userspace. |
| Microcontroller offload (Pico/ESP32 over USB serial) | any | yes | yes | no | firmware | More hardware than the problem. The ESP32-S3-BOX-3 satellite (`docs/esp32.md`) would do its own LEDs on its RMT peripheral, not via a Pi. |

Rust crates for the SPI route:

| Crate | What it adds | Verdict |
|---|---|---|
| `spidev` 0.7.1 | `Spidev::open` / `configure` / `transfer` — one `SPI_IOC_MESSAGE` ioctl per frame. Deps: `nix`, `libc`, `bitflags`. Linux-only. | **Chosen.** |
| `ws2812-spi` 0.5.1 + `smart-leds-trait` + `embedded-hal` 1.0 + `linux-embedded-hal` 0.5 | The same 4-bits-per-bit encoding. Its default writer issues one `SpiBus::write` per SPI byte — an ioctl each on Linux — and only its `hosted` module batches a frame. | Four crates for a lookup table, and the default path is a timing trap (a gap that reaches the reset time latches a partial frame). The encoder is written in-tree instead: ~30 lines, unit-tested, and it is the piece the client imports. |
| `rppal` 0.22.1 | A Pi HAL (GPIO/SPI/PWM/I2C); its SPI is spidev underneath; Pi 5 supported. | Sound, but a whole HAL for one ioctl; no advantage over `spidev` here. |

## The signal

Four SPI bits per LED bit — `1000` for a 0, `1110` for a 1 — at 3.2 MHz. Both
the BCM2835 and RP1 SPI blocks derive their clock by an integer divisor and
round the request down, so the second column is an example of what may
actually run:

| | WS2812B spec | at 3.2 MHz | at 3.125 MHz |
|---|---|---|---|
| bit period | 1.25 ± 0.6 µs | 1.25 µs | 1.28 µs |
| T0H (0 high) | 0.40 ± 0.15 µs | 0.31 µs | 0.32 µs |
| T1H (1 high) | 0.80 ± 0.15 µs | 0.94 µs | 0.96 µs |
| T0L | 0.85 ± 0.15 µs | 0.94 µs | 0.96 µs |
| T1L | 0.45 ± 0.15 µs | 0.31 µs | 0.32 µs |
| reset (400 µs of zeros) | ≥ 280 µs | 161 bytes | 165 bytes |

T1H sits at the top of its window and T1L at the bottom: the known compromise
of the 4-bit scheme, which `ws2812-spi` documents as working from 2.0 to
3.8 MHz and Adafruit's SPI NeoPixel driver uses the same way. The WS2812
decodes on the width of the high pulse and tolerates a long low, so the
high-side numbers are the ones that matter. Should the hardware check show
marginal decoding, the fallback is a 3-bits-per-bit encoding (`100` / `110`)
at 2.4 MHz, which gives T0H 0.42 µs and T1H 0.83 µs, near the centre of both
windows, at the cost of packing bits across byte boundaries.

A frame of 8 LEDs is 96 data bytes plus 161 reset bytes: 257 bytes, 0.64 ms on
the wire, one ioctl. spidev's default 4096-byte transfer ceiling allows about
320 LEDs before `spidev.bufsiz` has to be raised. On a Pi 4 the SPI clock
follows the core clock, which CPU idling moves; `core_freq=500` and
`core_freq_min=500` in `config.txt` pin it (rpi_ws281x README). The Pi 5's RP1
clocks SPI on its own.

## Decision

**SPI0 MOSI, `spidev`, our own encoder.**

1. **It is the one route that works on the Pi we have and the one we might
   have.** PIO is Pi 5-only; PWM and PCM DMA are Pi 4-and-earlier only; SPI is
   on both, on the same GPIO 10, through the same kernel interface.
2. **Unprivileged, with no rule of our own.** Pi OS's `99-com.rules` already
   puts `/dev/spidev*` in the `spi` group at 0660; the unit gains
   `SupplementaryGroups=audio spi`, the pattern it already uses for `/dev/snd`.
3. **No native code, no `Cross.toml` change.** `spidev` is a target-gated
   dependency (`[target.'cfg(target_os = "linux")']`); off Linux the strip type
   is a stub that fails at `open`, and the encoder and the scanner build and
   test everywhere, so the Mac workspace build stays green.
4. **The encoder is the integration artefact.** `crates/ws2812` is a library
   (`strip.rs`: `encode`, `Ws2812Spi::{open, write, clear}`; `color.rs`;
   `larson.rs`) that the demo binary and the client share; the client's LED
   work is a second sink behind the phase tracker that already drives the
   Jabra ring.
5. **Costs accepted.** The data wire moves from pin 12 to pin 19. SPI0 belongs
   to the strip on the satellite (another SPI device would go on SPI1 via an
   overlay). `dtparam=spi=on` becomes part of the Pi image: the installer
   writes it to `config.txt` and requires a reboot, as `run-on-pi.sh` does
   now, because applying it live hung the first run on the Pi 5 (Test
   strategy, incident).

Rejected: **RP1 PIO** — Pi 5-only, C library, root or udev, no Rust binding
(revisit if one appears). **`rpi_ws281x` PWM** — does not exist on the Pi 5,
needs root, and disables the Pi's analogue audio. **The `ws2812-spi` stack** —
per-byte ioctls on its default path, four crates for the same table.
**Microcontroller offload** — more hardware than an 8-LED indicator warrants
on a Pi that has a suitable peripheral.

## Vocabulary

What the strip shows for each phase of `crates/client/src/led.rs`, beside
what the Jabra ring shows for the same phase. The tracker derives the phases
and the mute overlay from the events a session already has; `Offline` is the
one state it never produces — the call loop sets it on the strip between
sessions, when there is no server to have a phase with, and the ring, which
is opened per session, is simply dark then.

| Phase | Meaning | Ring (Jabra) | Strip |
|---|---|---|---|
| Asleep | Armed, waiting for the wake word (wake mode only). Also the resting state every sink is put to when a session ends. | dark | One green pixel at the idle brightness, sweeping end to end and back over 5 s — the kit's "skinny eye" reduced to a lone pixel, which splits across two LEDs as it crosses between them. |
| Listening | Awake; audio streams to the server. | solid green | Every LED green at the idle brightness, steady. |
| Thinking | The user's turn is in; the server is working on it. | solid green | The Larson scanner at full brightness, 700 ms a pass, the palette's next colour each pass, restarted from the low end for every thinking spell. |
| Speaking | The bot's audio is playing. | solid green | Every LED a soft warm white (255, 120, 40 scaled by the brightness), steady. |
| + muted | The server has gated the mic; an overlay on any awake phase. | solid red instead of green | Both end pixels red at full brightness, painted over the phase's pattern (the scanner keeps running between them). |
| Offline | No server: unreachable, or the connection dropped. Between sessions. | dark | Pixel 0 amber (255, 150, 0) at the idle brightness, one second on, one second off. |
| — | The client exits. | dark | dark |

The rules behind the table:

- **Two brightness levels.** `LED_STRIP_BRIGHTNESS` (0.2) is for the states
  that last seconds — thinking, speaking, the mute overlay.
  `LED_STRIP_IDLE_BRIGHTNESS` (0.05) is for the ones that last hours —
  asleep, listening, offline — so a pattern that is on all evening in a
  living room stays out of the way.
- **Motion means something is happening.** The fast, wide, coloured scanner
  is thinking; the slow lone pixel is "alive and armed"; the slow blink is a
  fault. Listening and speaking are still, so they never compete with the
  conversation.
- **One colour per meaning.** Green is the microphone path (armed, then
  open). The palette is thinking. Warm white is the bot's own voice. Red is
  the mic gated. Amber is a fault. Nothing else uses those colours.
- **Static phases cost one write; animated phases a frame per step**
  (6 ms for thinking, 45 ms for asleep, 1 s for offline), on the strip's own
  thread, never on the driver's blocking pool.
- **The strip outlives sessions.** It is opened once per call and handed to
  each session as a handle, so the retry loop can show Offline after a
  session ends and the session's own start state overrides it. The ring is
  still opened per session, since unplugging it ends the session anyway.

Refinements left for later: a listening fill that shrinks as the wake
session's silence timeout runs down (the client has the timer), and a
night-time dimming schedule. And the test strip's last LED has a dead green
die, so the idle pixel vanishes for a step at that end until the strip is
replaced.

## Test strategy

**Unit, no hardware** (`cargo test -p voice-chatbot-ws2812`, 19 tests):
encoder bytes against hand-worked patterns and the GRB/RGB swap; frame size
and reset length at several clocks; scanner frames against values computed
from `larson.c` (positions 0, 112 and 127 on the kit's nine LEDs); the down
pass as the mirror of the up pass one sub-step later, with the one-frame dwell
at the low end the firmware has; two-, three- and four-LED strips staying in
bounds; CLI parsing. Clippy `-D warnings` on the crate and the workspace; the
cross-build yields an aarch64 ELF (all verified 2026-09-03).

**Hardware, open gates** (the Pi is reachable only by password, so these are
run by hand from the dev machine):

1. `make ws2812-pi WS2812_ARGS="--pattern wiring"` — all LEDs red, green,
   blue, white for a second each, then one LED at a time from index 0. Wrong
   colours mean `--order rgb`; the walk confirms which end is index 0.
2. `make ws2812-pi` — the scanner for several minutes at default brightness
   with no flicker, stray colours or stuck pixels.
3. `--brightness 1 --colors white` briefly — no brown-out or reset on the Pi.
4. `run-on-pi.sh` on a fresh Pi OS — it writes `dtparam=spi=on`, the reboot
   it asks for brings up `/dev/spidev0.0`, and the binary runs from the `spi`
   group without sudo.

**Incident, 2026-09-03.** The first version of `run-on-pi.sh` enabled SPI
with `raspi-config nonint do_spi 0`, which edits `config.txt` and then runs
`dtparam spi=on` to apply the overlay at runtime. On the Pi 5 the run hung
as soon as that step started: no further output, Ctrl-C ignored, and a
second session over the same ssh ControlMaster socket hung too, while the
board kept answering ping and fresh ssh logins. Afterwards `config.txt`
carried `dtparam=spi=on`, no `/dev/spidev0.0` existed (only the Pi 5's stock
`spidev10.0`, an internal bus), and the process was gone once the stale
master on the dev machine was killed. Whether the runtime overlay blocked or
the multiplexed pty session wedged was not pinned down. Either way the live
apply is a step nothing here needs, and Raspberry Pi's own guidance is that
runtime overlay application is best-effort while firmware application at
boot is the reliable path, so the script now only edits `config.txt` and
asks for a reboot. The same rule applies to `install.sh` when the client
integration turns SPI on.

## Consequences

- **Client integration (done 2026-09-03).** `Strip` in
  `crates/client/src/led/strip.rs` is a second `LedSink` behind the phase
  tracker that drives the Jabra ring (the sink trait now takes the
  `Indication`, and the controller fans out to every sink, dropping one whose
  write fails). A thread owns the device and renders the vocabulary above;
  the strip is opened once per call and outlives sessions. `LED_STRIP=auto|off`,
  `LED_STRIP_COUNT`, `LED_STRIP_BRIGHTNESS`, `LED_STRIP_IDLE_BRIGHTNESS` in
  the Pi's `.env`; the unit gained the `spi` group and `install.sh` enables
  SPI in `config.txt`. `led-test` walks both devices through every state.
- **Frame writes stay on the strip's own thread.** 0.64 ms per frame is
  nothing for the bus, but 160 a second is more than the ring's write-per-
  change model wants on the blocking pool, so the strip animates itself
  between the indications the driver hands it.
- **The demo binary stays** in the library crate as the hardware check
  (`make ws2812-pi`), the way `led-test` is for the ring.
- **Licensing note.** `larson.c` is GPL; `larson.rs` re-implements its
  arithmetic (about sixty lines) with attribution. Check licence compatibility
  before this repository is distributed under anything else.
- **A Pi 4 satellite** needs the `core_freq` pins above; nothing else changes.

## Re-evaluation triggers

1. The hardware gates fail after the listed fallbacks — revisit PIO (Pi 5) or
   microcontroller offload.
2. A maintained Rust binding for the RP1 PIO appears — GPIO 18, or any pin,
   becomes possible for a Pi 5-only fleet.
3. More than ~300 LEDs, or several strips — `spidev.bufsiz`, SPI1 on GPIO 20
   via overlay, or offload.
4. RGBW (SK6812) strips — 32-bit pixels; an encoder change only.
5. The satellite hardware changes (ESP32-S3-BOX-3, `docs/esp32.md`) — RMT on
   the ESP32; outside this ADR.
